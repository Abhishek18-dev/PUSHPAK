1. Executive Summary
This document specifies the product requirements and technical design for a software-based, simulation-only research prototype
that studies intelligent RF spectrum scan scheduling. A receiver with limited instantaneous bandwidth cannot observe an entire simulated
spectrum at once. A fixed, open-loop scan pattern wastes time revisiting quiet bands and can miss or delay detection of periodic or
frequency-agile emitters. This system builds a configurable RF environment simulator, a receiver model, an open-loop baseline scanner,
and a machine-learning-driven scheduler that learns ΓÇö from simulated scan outcomes ΓÇö which band to observe next, and for how long, in
order to maximize detection while minimizing wasted scan time.
The prototype is intentionally scoped as a research and demonstration platform. It does not control real RF hardware, does not
intercept real-world communications, and does not perform jamming, electronic attack, or weapon targeting of any kind. All emitters,
signals, and detections exist only inside a synthetic, deterministic-by-seed simulation.
The recommended MVP scheduler is a contextual multi-armed bandit, upgradeable to tabular Q-Learning and, as a stretch goal, a
Deep Q-Network (DQN), based on the trade-off analysis in Section 26. The system is evaluated against the open-loop baseline using
probability of detection (Pd), probability of false alarm (Pfa), average intercept time, and detection latency, across seven emitter-mix
scenarios (Section 13). A live dashboard visualizes the spectrum, receiver state, scheduler decisions, and baseline-vs-ML comparison in a
scripted 3ΓÇô5 minute demo (Section 20).

2. Problem Statement & Background
2.1 Problem Statement
A receiver has a limited instantaneous bandwidth and cannot observe the entire spectrum simultaneously. Traditional open-loop scanning
follows a fixed pattern (e.g., round-robin across bands at a fixed dwell time), which can cause important emitters to be missed or detected
late ΓÇö particularly when emitters are periodic, frequency-agile, or otherwise dynamic. The system must produce a simulated RF
environment and an AI/ML-driven scan scheduler that learns, from previous scan outcomes, which band to scan, when, and for how long, in
order to maximize useful detection while minimizing unnecessary scanning and intercept time.
2.2 Background
Open-loop, round-robin scanning is simple and predictable but treats every band as equally likely to carry activity at every point in time. In
real spectra, activity is highly non-uniform: some emitters transmit continuously, some are periodic bursts, and some hop frequency
pseudo-randomly. A scheduler that models band activity from its own scan history can allocate more of the receiver's limited dwell time to
bands that are currently or predictably active, and less to bands that are historically quiet ΓÇö a classic explore/exploit resource-allocation
problem, which maps naturally onto multi-armed bandit and reinforcement-learning formulations.
2.3 Why This Matters for the Prototype
Demonstrates a measurable, reproducible improvement of a learned policy over a fixed baseline on identical simulated scenarios.
Provides an extensible research platform: new emitter behaviors, receiver constraints, and scheduling algorithms can be added without
re-architecting the system.
Keeps the entire capability inside a closed simulation boundary appropriate for a hackathon/research prototype (see Section 16,
Security).
3. Goals & Non-Goals
3.1 Goals
1. Build a configurable, reproducible simulated RF spectrum with ground-truth labels.
2. Model a bandwidth-constrained receiver with realistic scan/tune/dwell constraints.
3. Implement an open-loop baseline scanner as the control condition.
4. Implement a learning-based scheduler (bandit ΓåÆ Q-Learning ΓåÆ optional DQN/PPO) that outperforms the baseline on defined metrics.
5. Provide a mathematically defined, reproducible evaluation harness (Pd, Pfa, intercept time, latency, efficiency).
6. Explicitly model and evaluate periodic-emitter prediction.
7. Provide a real-time dashboard suitable for technical and non-technical audiences.
8. Keep the system strictly simulation-only, auditable, and extensible.
3.2 Non-Goals
No control of, or interface to, real RF hardware or SDR devices.

No real-world signal interception, direction-finding, or geolocation of actual emitters.
No jamming, spoofing, electronic-attack, or countermeasure functionality.
No weapon-system targeting, cueing, or fire-control integration.
No use of classified, export-controlled, or operationally sensitive data or waveforms.

8.2 Simulation Loop (Pseudocode)
for t in range(0, T, step):
    spectrum.advance(t)                     # update ground-truth occupancy
    action = scheduler.decide(state)        # baseline or ML policy
    observation = scanner.execute(action, receiver, spectrum)
    event = detection_engine.evaluate(observation, threshold)
    reward = reward_fn(event, action, state)
    state = state_builder.update(state, action, observation, event)
    metrics.record(t, action, observation, event, reward)
    scheduler.learn(state, action, reward)  # no-op for baseline

9. Receiver Model
9.1 Formal Definitions
Concept
Definition
Receiver state R(t)
Tuple (bands currently tuned, remaining dwell time, tuning-delay countdown, scan history window).
Scan action a(t)
Subset of bands of size Γëñ K (instantaneous bandwidth), plus optional dwell time d.
Observation o(t)
Noisy measurement per scanned band: signal-present likelihood or SNR estimate.

Observation exceeds the detection threshold and ground truth = active (true positive).

Ground truth = active but band not scanned, or scanned observation below threshold (false negative).

9.2 Configurable Parameters

Total spectrum: N configurable bands (default 16, tested up to 64).
Instantaneous bandwidth: K bands observable per step (default K=2, K Γëñ N).
Dwell time: minimum observation duration per band, configurable per scan action.
Tuning/switching delay: fixed cost applied when the receiver retunes to a previously unobserved band.
Detection threshold: SNR or likelihood cut-off; tunable to trade Pd against Pfa.
The receiver never interacts with physical hardware; all observations are generated by the simulator's noise model applied to the ground-
truth occupancy table.

10.4 Episode, Exploration & Training Definitions
Episode: one full simulation run of fixed duration T; terminal state at t = T.
Observation space: per-band feature vectors described in ML-001, flattened for the bandit/tabular agent.
Exploration: ╬╡-greedy for bandit/Q-Learning (╬╡ decayed per episode); entropy-regularized policy for PPO.
Exploitation: argmax expected reward (bandit/Q-Learning); policy network sampling (DQN/PPO).
Checkpointing: model weights/Q-table snapshot every N episodes and on best-validation-reward.
Versioning: every trained model registered with algorithm, hyperparameters, training-data seed range, and evaluation metrics (see
Section 24, ML pipeline).
11. Periodic Emitter Handling
Periodic emitters are the primary motivation for moving beyond open-loop scanning: a fixed round-robin pattern that happens to poll a
band during its OFF phase will systematically miss or delay detection. The prototype addresses this with a dedicated, lightweight statistical
predictor rather than folding period estimation into the RL policy itself.
11.1 Recommended Architecture: Hybrid Predictor + Scheduler
A separate PeriodicityEstimator module tracks each band's detection timestamps and fits a simple autocorrelation/inter-arrival estimate
of period length and phase. Its output ΓÇö predicted next-active-window and a confidence score ΓÇö is exposed as additional features in the
RL state vector (ML-001), not as a standalone decision-maker. This keeps the RL policy responsible for the actual scan trade-off while the
statistical estimator specializes in the narrower, more data-efficient problem of periodicity detection.
Option
Why Not Chosen as Primary
Fold periodicity purely into RL state,
no separate model
RL requires far more samples to learn periodicity implicitly than a closed-form estimator; slower convergence for MVP
timeline.

Separate ML model (learned
periodicity classifier)
Overkill for MVP; a statistical inter-arrival estimator is simpler, interpretable, and sufficient for the defined emitter
classes.

15. Backend Architecture, WebSocket & API Specification
15.1 Backend Stack & Layering
The core application backend is built on Java 21 + Spring Boot 3 (Spring Web MVC, Spring Data JPA, Spring WebSocket, Spring
Validation, Spring Security for V1 auth), with PostgreSQL as the system of record and Flyway for versioned schema migrations. Redis
(Spring Data Redis) provides pub/sub fan-out for WebSocket broadcast across instances and backs the async job queue for long-running
training/experiment jobs. Layers: Controller ΓåÆ Service ΓåÆ Repository ΓåÆ Entity , with request/response DTOs (Java records) validated via
jakarta.validation annotations, a centralized @RestControllerAdvice exception handler mapping domain exceptions to the standard error
envelope (Section 20.2), and structured JSON logging via SLF4J + Logback.
The RL/bandit algorithms themselves (Section 15.5) run in a small, dedicated Python ML microservice rather than inside the Java
backend, since the RL/scientific-computing ecosystem (Gymnasium, NumPy, Stable-Baselines3) is Python-native. The Spring Boot
SchedulerService calls this microservice over an internal REST contract ( /internal/decide , /internal/train ) ΓÇö this boundary is
documented as ADR-06 in Section 26.

Reconnection
Client exponential backoff (1sΓåÆ30s cap); server replays last known state snapshot on reconnect.

Server coalesces spectrum_update events to at most 10/s per connection under load; drops intermediate frames, never the

17. Security
Control
Description
Simulation-only boundary
No module, driver, or dependency provides access to physical RF hardware, SDR devices, or external radios (NFR-
010); enforced via dependency allow-list review.
No real-world interception/attack
All signal generation is synthetic; no code path accepts or transmits live RF/network capture data.
API authentication (V1)
Bearer JWT with short-lived access tokens; MVP demo runs without auth on a trusted local network.
Input validation
All request DTOs validated via jakarta.validation (Bean Validation) annotations; reject on constraint violation
with HTTP 422.
Rate limiting
Token-bucket limiter (Bucket4j) on write endpoints (e.g., 60 req/min per client) to protect the simulation worker pool.
Secrets management
Environment-variable-based secrets via .env / Spring application.yml profiles (never committed); production
uses a secrets manager.
Dependency security
Automated dependency vulnerability scan in CI (e.g., OWASP Dependency-Check / mvn versions:display-
dependency-updates for the backend, npm audit for the frontend, pip-audit for the ML microservice).
Audit logging
All model activation and configuration-change endpoints write an audit-log entry with actor and timestamp.
Data protection
No PII is collected or stored; simulation data is synthetic.

(5) a final side-by-side comparison chart with the headline improvement number.

28. Definition of Done, Future Scope & Appendix
28.1 Project-Level Definition of Done
1. A simulated RF environment can be created with configurable bands, duration, and seed.
2. All five emitter behavior classes can be simulated with correct ground truth.
3. The receiver model correctly enforces instantaneous bandwidth, dwell, and tuning-delay constraints.
4. The open-loop baseline scanner runs deterministically for a given seed.
5. The ML scheduler produces scan decisions that adapt to observed activity.
6. Pd, Pfa, and average intercept time are computed correctly against hand-verified test cases.
7. Baseline vs. ML results can be compared for the same scenario/seed.
8. Periodic-emitter prediction measurably improves detection latency on Scenario B.
9. All Section 15.3 APIs function end-to-end from the dashboard.
10. The system runs entirely without real RF hardware, confirmed via dependency audit (Section 17).
11. The 3ΓÇô5 minute demo runs reliably twice consecutively.
28.2 Future Scope Summary
V1: Q-Learning scheduler option, full 7-scenario suite, periodicity feeding into state, model registry with rollback, authentication. V2: Deep
RL (DQN/PPO), neural contextual bandit, multi-receiver scenarios, transfer learning across scenario families, automated hyperparameter
search, adversarial frequency-agile stress testing.
